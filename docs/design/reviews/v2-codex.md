# v2 設計レビュー（Codex）

対象: 6b28750 の docs/design/v2.md と作業票。指摘はすべて次のコミットで反映。

## 高

- **失敗・強制終了時にジョブが残留する。** [`v2.md` のジョブの流れ](<docs/design/v2.md:105>) は、worktree 作成やバックグラウンド起動が途中で失敗した場合、またはランナーが強制終了した場合の状態遷移を定めていません。`queued` / `running` のまま残り、`wait` が終わらない可能性があります。worktree 作成失敗時の片付け、全終了経路での `failed` 記録、起動済みかを見分ける方法を定義してください。状態・結果ファイルは一時ファイルからの rename で更新すると、読み取り途中の破損も避けられます。

- **パッチ適用失敗時に作業ツリーを変えない保証が具体化されていない。** [`v2.md` の `apply`](<docs/design/v2.md:40>) は `git apply --3way`、[`05-manage.md`](<docs/design/v2/05-manage.md:12>) は失敗時に変更しない、とだけ指定しています。3-way 適用で競合した場合の作業ツリーや index の状態が未定義です。失敗時に元の状態へ戻す保証を設けるか、適用前チェックと競合時の復元手順を明記してください。index と作業ツリーを同時に触る別プロセスとの競合も扱いが必要です。

- **ジョブ ID の衝突時に既存ジョブを壊すおそれがある。** [`v2.md` の ID 仕様](<docs/design/v2.md:74>) は時刻と 4 桁の乱数に依存し、衝突時の動作を定めていません。並行 submit や同時刻の大量発行で、既存ディレクトリを上書きする実装になり得ます。ジョブディレクトリを排他的に作成し、衝突したら ID を生成し直すことを仕様に加えてください。

## 中

- **「03 と 04 は並行可能」という計画と作業票のファイル範囲が衝突する。** [`00-plan.md`](<docs/design/v2/00-plan.md:15>) は並行委任可能としていますが、両票が [`bin/subcon`](<docs/design/v2/03-new-guide.md:9>) を変更対象にしています。並行に適用・検収すると変更が競合します。共通の振り分け部分を先に上位が仕上げて各票から外すか、03 と 04 を明確に順次実行する計画にしてください。

- **`wait` が永久に待ち続ける条件とタイムアウト動作が未決のまま。** [`v2.md` の未決事項](<docs/design/v2.md:189>) ではタイムアウトを保留し、[`04-jobs.md`](<docs/design/v2/04-jobs.md:24>) はポーリング間隔だけを指定しています。バックグラウンド起動に失敗して状態が更新されない場合や、agy が停止しない場合に上位エージェントの呼び出しが終わりません。v2 の範囲でタイムアウトを決め、期限到達時の終了コードとジョブ状態を定義してください。

- **複数票の `submit` で部分成功する場合の契約がない。** [`v2.md` の submit 手順](<docs/design/v2.md:107>) は票ごとに作成するとしていますが、後の票が不正、worktree 作成失敗、または起動失敗したとき、先に作ったジョブを残すのか、どの ID を stdout に返すのかが不明です。全票を先に検証してから開始するのか、部分成功を許すなら JSON に成功・失敗を票ごとに含めるのかを決めてください。

- **チェック対象のファイル名とパス安全性が定義不足。** [`v2.md` の `outside_files`](<docs/design/v2.md:99>) は票の `## Files` との比較ですが、相対パスの正規化、絶対パスや `..` の拒否、重複・glob の扱いがありません。文字列比較だけでは `a/../b` のような別表記を誤判定し得ます。票のパス書式を制限し、正規化後のリポジトリ相対パスで照合する仕様を加えてください。

- **未コミットの票を発行した場合、票だけがジョブに入り設計上の前提と食い違う。** [`v2.md`](<docs/design/v2.md:14>) は未コミット変更をジョブに含めないとしますが、[`ticket.md` のコピー手順](<docs/design/v2.md:66>) は発行時点のファイルを保存します。票が未コミットでもコピーできるため、Flash は HEAD にない仕様で実装することになります。票が HEAD に存在することを必須にするか、未コミット票を許容する旨と結果の再現性への影響を明記してください。

- **Flash 向けの実装範囲が広く、作業票から判断を補う必要がある。** [`04-jobs.md`](<docs/design/v2/04-jobs.md:12>) は設計書の複数節を一括参照し、`--runner` の許容値、オプションの競合、`show` の実行中表示、失敗時に `patch.diff` を残すかなどを直接指定していません。安価なモデルに推測させないため、許容値・異常系・状態ごとの出力と終了コードを作業票へ列挙してください。

## 低

- **`work/` の保存仕様と終了後削除の関係が読み取りにくい。** [`v2.md` の保存場所と後処理](<docs/design/v2.md:63>) では `work/` をジョブ内ファイルとして掲げつつ、後処理で削除するとしています。`work/` は一時領域で、保存対象ではないと表に注記すると、`discard` や失敗時の削除要件も整理しやすくなります。

- **`list --all` とグローバルな状態保存の境界が曖昧。** [`v2.md`](<docs/design/v2.md:37>) は全リポジトリの一覧を許しますが、対象リポジトリの識別・削除・適用制限を定めていません。`--all` での表示だけを許すのか、他リポジトリの job に対する `show` / `diff` / `discard` / `apply` も許すのかを決め、少なくとも `apply` はベースのリポジトリ確認と基底 commit の存在確認を仕様化してください。
