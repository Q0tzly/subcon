# ベンチマーク計画（未実施）

ここには何をどう測るかだけを書く。進め方は次のとおり（2026-11-11 に決定）。

## 進め方（2026-11-11 決定）

Claude の利用上限が厳しいため、フル版はやらない。2 つに割る。

- **実装役は縮小版を先にやる**: 実装モデルは agy 経由で切り替えるので、Claude モデル（Sonnet / Opus）も Antigravity 側の枠で回り、Claude の上限を食わない。題材は票 03（易）と票 11（中）の 2 枚、モデルは Flash medium / Sonnet medium / Opus medium、まずは各 1 回（計 6 ジョブ）。監督は固定し、検収は最小限にする。ばらつきが問題になったら回数を足す
- **監督役の比較は延期する**: 監督役のサブエージェントと見逃し判定の独立レビューはどちらも Claude の枠を食う。上限に余裕のある週に回すか、独立レビュー役を Claude 以外のモデルにする案で再設計する
- 実作業で subcon を使い続ければ `stats` に実データが溜まる。人工的に票を流し直すベンチマークの優先度は、実データの蓄積より下でよい

## きっかけ

`subcon stats` の票 10・11 で、Flash（実装）は 1 票あたり約 29 万トークン、Sonnet（監督のサブエージェント）は 2 票で約 8 万トークンだった。
ただしこの差は**役割の差**が大きく、モデルの差とは言えない。

- 実装役は何ターンも回る（読む → 書く → テスト → 直す）。agy の `input_tokens` は毎ターン送り直す文脈の累計なので、ターン数に比例して膨らむ
- 監督役は diff を読んでテストを回すだけで、ターン数が少ない
- トークン数とコストは別物。単価がモデルで大きく違い、キャッシュ読み出しはさらに安い

同じ役割でモデルを入れ替えたときの差を、条件を揃えて測る。

## 問い

1. **実装役**: 同じ票を Flash（low / medium / high）・Sonnet・Opus に渡すと、成功率・手戻り・トークン・時間・コストはどれだけ違うか。agy は Claude のモデルも選べるので、`subcon submit --model <ID>` を変えるだけで測れる
2. **監督役**: 同じ Flash の成果物を Sonnet と Opus に検収させると、見逃し（後から独立レビューで見つかる問題）の数とトークンはどれだけ違うか
3. 組み合わせとして、どこまで安くしても品質が落ちないか

## 題材

- 合格テストのある既存の票を使う。各票の土台コミット（票の直前の状態）から始め、合格テストは票のコミット時点のものを使う
  - v2: 03（new / guide）、04（submit）、05（wait / show）、06（list / apply）
  - v2.2: 10（history）、11（stats）
- 難しさに幅を持たせる（03 は易しい、04 は難しい）
- テストに出ない不具合を仕込んだ票を 1〜2 枚足すと、監督役の見逃しを測りやすい（例: シグナル処理、サブディレクトリからの実行）

## 測るもの

| 指標 | 取り方 |
| --- | --- |
| 成功（合格テストが通り、範囲チェックも OK） | `result.json` と、上位による合格テストの再実行 |
| 手戻り（再委任の回数、上位が直した行数） | 監督役の報告とコミットの diff |
| 見逃し | 監督役が通したコミットを、別の強いモデルが独立にレビューして見つかった問題の数 |
| トークン（入力・出力・キャッシュ読み出し・思考） | 実装役は agy の `usage`、監督役はサブエージェントの使用量 |
| 時間 | agy の `duration_seconds`、監督役は開始から報告まで |
| コスト | トークン × 各モデルの単価（実施時点の価格を調べる） |

## やり方

- フル版では各組み合わせを 3 回ずつ回す（ばらつきが大きいため）。同じ土台コミット・同じ票・同じテスト。ただし縮小版（上記「進め方」）では各 1 回から始める
- 実装役の比較: 監督は固定（例: Opus）し、実装モデルだけを変える
- 監督役の比較: 実装の成果物（パッチ）を固定し、監督モデルだけを変える。同じパッチを渡すので、見逃しを公平に比べられる
- 結果は `docs/benchmarks/<日付>.md` に表で残す
