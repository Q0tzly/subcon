# ベンチマーク記録 2026-11-11（実装役・縮小版）

計画は `docs/design/benchmark.md`。縮小版として票03（易）と票11（中）を各モデル1回ずつ流し、監督（Muse）が全パッチに受け入れテストを別クローンで再実行して検収した。追加で票04（難）を Haiku 直回しで1回、票03・11 を Haiku の subcon 経由（シム）でもう1回ずつ流した。

## 条件の違い（重要）

- **agy 経由**: 通常の subcon ジョブ。`lib/prompt.md` の封筒＋JSON Schema レポート、worktree 隔離、ホスト側 Acceptance。モデルは Flash / Sonnet / Opus（いずれも medium、Antigravity のサブスク枠で実行）
- **Haiku 直回し**: `claude -p` をベンチパックに直接実行。読み取り範囲を列挙した手書きの節約プロンプトで、subcon の封筒・スキーマ強制・範囲チェックは通していない（条件が緩い）
- **Haiku（subcon 経由・シム）**: agy の CLI 形状を真似たシム（`agy` の振りをして中身は `claude -p --model haiku`）をランナーに差し、agy 組と完全に同じ封筒・スキーマ・隔離・Acceptance で実行。直回しとの差が「頼み方（ハーネス）」の差になる。MCP はシム側で無効化（`--strict-mcp-config`＋空設定）

トークン数の数え方は経路で異なる（agy はターンごとの文脈再送を含む累計、claude は API 使用量）。コストは Haiku のみリスト価格換算（agy 組はサブスク枠のため金額換算なし）。

## 所見

- **Haiku は同条件でも性能が落ちなかった。** 票03は done・9/9（62.6s・$0.0201、直回しの 77s・$0.0194 とほぼ同等）。票11も実装は 8/8 相当を提出した。直回しの好成績は節約プロンプト（頼み方）のおかげではなかった
- **ハーネス税は中難度で見える。** 票11では時間 +32%（114s→150s）、コスト +49%（$0.0202→$0.0301）。封筒の文脈と読み取り範囲を絞らない分。票03ではほぼゼロだった
- **難票では逆に速く安かった。** 票04はシム経由が 234.6s・$0.0642 で、直回し（539.4s・$0.1181）の半分以下。n=1 のばらつきはあり得るが、「封筒が重いと性能が落ちる」という仮説は3票とも支持されなかった。封筒の構造化（範囲・受け入れ・報告形式の明示）が難票では効いた可能性がある
- **スキーマ封筒は報告の質を上げた。** Haiku（シム）は票11で失敗5件の原因が自分の実装ではなくテストハーネスの BSD date 依存だと切り分け、範囲外の `tests/` には触れず、/tmp コピーで 8/8 を証明した上で partial と申告した。環境側の不具合を診断できたのは全モデル中でこれだけ
- **票11の本当の失敗は Flash だけ。** 194k トークンを消費して空パッチ（0/8）。Sonnet / Opus のジョブ失敗はクォータ枯渇が原因で、実装自体は完成していた（上記訂正のとおり）
- **agy 経由の Claude モデルは可用性が弱点。** Sonnet / Opus とも Antigravity の個人クォータをベンチ中に枯渇させた（リセット 11/16 頃）。Sonnet はエラー後も約26分ハングしてから timeout で確定する挙動も含め、無人運用では詰まり方が読みにくい
- 留保: 各組み合わせ1回のみ。票11の Haiku 直回しはハーネス状態の異なる別コピーで実施したため、最も統制の取れた比較は票03と、ハーネス修正後の再検収による票11の横並びである
