# ベンチマーク記録 2026-11-11（実装役・縮小版）

計画は `docs/design/benchmark.md`。縮小版として票03（易）と票11（中）を各モデル1回ずつ流し、監督（Muse）が全パッチに受け入れテストを別クローンで再実行して検収した。追加で票04（難）を Haiku 直回しで1回、票03・11 を Haiku の subcon 経由（シム）でもう1回ずつ流した。

## 条件の違い（重要）

- **agy 経由**: 通常の subcon ジョブ。`lib/prompt.md` の封筒＋JSON Schema レポート、worktree 隔離、ホスト側 Acceptance。モデルは Flash / Sonnet / Opus（いずれも medium、Antigravity のサブスク枠で実行）
- **Haiku 直回し**: `claude -p` をベンチパックに直接実行。読み取り範囲を列挙した手書きの節約プロンプトで、subcon の封筒・スキーマ強制・範囲チェックは通していない（条件が緩い）
- **Haiku（subcon 経由・シム）**: agy の CLI 形状を真似たシム（`agy` の振りをして中身は `claude -p --model haiku`）をランナーに差し、agy 組と完全に同じ封筒・スキーマ・隔離・Acceptance で実行。直回しとの差が「頼み方（ハーネス）」の差になる。MCP はシム側で無効化（`--strict-mcp-config`＋空設定）

トークン数の数え方は経路で異なる（agy はターンごとの文脈再送を含む累計、claude は API 使用量）。コストは Haiku のみリスト価格換算（agy 組はサブスク枠のため金額換算なし）。

## 所見

- **Haiku は同条件でも性能が落ちなかった。** 票03は done・9/9（62.6s・$0.0201、直回しの 77s・$0.0194 とほぼ同等）。票11も実装は 8/8 相当を提出した。直回しの好成績は節約プロンプト（頼み方）のおかげではなかった
- **ハーネス税は中難度で見える。** 票11では時間 +32%（114s→150s）、コスト +49%（$0.0202→$0.0301）。封筒の文脈と読み取り範囲を絞らない分。票03ではほぼゼロだった
- **難票では逆に速く安かった。** 票04はシム経由が 234.6s・$0.0642 で、直回し（539.4s・$0.1181）の半分以下。n=1 のばらつきはあり得るが、「封筒が重いと性能が落ちる」という仮説は3票とも支持されなかった。封筒の構造化（範囲・受け入れ・報告形式の明示）が難票では効いた可能性がある
- **スキーマ封筒は報告の質を上げた。** Haiku（シム）は票11で失敗5件の原因が自分の実装ではなくテストハーネスの BSD date 依存だと切り分け、範囲外の `tests/` には触れず、/tmp コピーで 8/8 を証明した上で partial と申告した。環境側の不具合を診断できたのは全モデル中でこれだけ
- **票11の本当の失敗は Flash だけ。** 194k トークンを消費して空パッチ（0/8）。Sonnet / Opus のジョブ失敗はクォータ枯渇が原因で、実装自体は完成していた（上記訂正のとおり）
- **agy 経由の Claude モデルは可用性が弱点。** Sonnet / Opus とも Antigravity の個人クォータをベンチ中に枯渇させた（リセット 11/16 頃）。Sonnet はエラー後も約26分ハングしてから timeout で確定する挙動も含め、無人運用では詰まり方が読みにくい
- 留保: 各組み合わせ1回のみ。票11の Haiku 直回しはハーネス状態の異なる別コピーで実施したため、最も統制の取れた比較は票03と、ハーネス修正後の再検収による票11の横並びである

## 追加実験（同日深夜）: 票20（CI ランナー本体）— Haiku（シム）のみ

難易度を一段上げた追加の1本。題材は `runners/ci` の新規実装（gh で Actions を起動し、run を表示名で突き合わせてポーリング、締め切りで cancel、artifact を回収・展開）。パックは土台コミット `67f47dd` のツリーを履歴なし1コミットにしたもの。開始状態は cirunner 0/3・全スイート 85 pass / 3 fail（落ちているのは cirunner の3件のみ）を確認済み。Acceptance は `tests/run.sh cirunner` ＋全スイート全通過。

| モデル | 経路 | 時間 | 出力 | キャッシュ読 | コスト | diff | 監督検収 |
|---|---|---|---|---|---|---|---|
| Haiku 5.5 | subcon（シム） | 108.8s | 13,608 | 268,792 | $0.0185 | runners/ci +89（本番実装は Flash の +134） | cirunner 2/3・全スイート 87/88※ |

※ 唯一の失敗 `test_cirunner_gh_missing` はテスト側の環境依存: テストは `PATH=$d:/usr/bin:/bin` で gh が見えない前提だが、この VM では gh が `/usr/bin/gh` に実在するため前提が成立しない。Haiku は自分の申告（partial）の中でこの切り分けまで報告し、gh の無い PATH でランナーを直接実行して「exit 1＋gh not found」を別途確認していた。監督の再実行結果も一致（2/3、87/88）。なお本家でも後に同じテストが同じ理由で直されている（`fc9cc56` "Hide gh by exclusion PATH in cipre gh-missing test"）。

所見（追加）:

- 実装自体は契約どおり完成しており、本番実装より小さい（+89 vs +134）。「外部システムとの契約を読む」種の難しさでも速度・コストは易い票並みだった（108.8s・$0.0185）
- Haiku の partial 申告は票11・票20とも「実装の不足」ではなく「テストハーネスの環境依存の診断」だった。2回とも診断は正しく、2回とも本家で後に同じ箇所が直されている。自分のバグと世界のバグを分けて報告できるのは、監督する側から見て大きな長所

## 追加実験（同日深夜）: 票25（ファイル形式の版付け）— Haiku（シム）のみ

複数ファイルにまたがる整合性が難しい1本。meta.json / result.json / history.jsonl の全生産者に `v: 1` を入れ、history 行種別の判定を `.type` に統一する。パックは土台コミット `c9d8b48` のツリー（履歴なし1コミット）。開始状態は formats 1/5（後方互換の番人のみ通過）・全スイート 111 pass / 4 fail で、票の Notes の記述と一致。

| モデル | 経路 | 時間 | 出力 | キャッシュ読 | コスト | diff | 監督検収 |
|---|---|---|---|---|---|---|---|
| Haiku 5.5 | subcon（シム） | 98.0s | 6,709 | 401,175 | $0.0150 | 4ファイル +10/-6（本番は +11/-6 相当＋補完1行） | formats 4/5・全スイート 114/115※ |

※ 唯一の失敗 `test_formats_running_result_v`（実行中ジョブの合成結果への v 付け）は、実装箇所が `lib/query.sh` の `job_result` で、**票の `## Files` に含まれていない**。本番でも Flash の実装後に監督の補完コミット（`b6c53c0`「票25の Files 漏れの補完」）が必要だった箇所。Haiku は範囲を守って query.sh を触らず、partial の申告の中で「Interface は合成結果への v を求めているが実装箇所は Files 外の query.sh（40行目前後）にある。Files に query.sh を足して合成 object に `v: 1` を1行入れれば通る見込み」と、落ちているテスト名まで特定して報告した。監督がその処方どおり1行を足して再実行したところ formats 5/5・全スイート 115/115 を確認した。

所見（追加）:

- 複数ファイルの整合でも漏れは「範囲内の実装」には無かった。残った1件は票自体の Files と Interface の矛盾であり、Haiku は「黙って範囲を出る」でも「黙って漏らす」でもなく、**範囲を守った上で矛盾を正確にエスカレーションする**という、委任の作法として最も正しい捌き方をした。本番の Flash 実装（監督の補完コミットで完成）より、監督側の手間は小さい
- あわせて「合成結果の形が lib/job.sh の finalize と lib/query.sh の job_result で二重管理になっていてずれやすい」という構造側の問題も issues に挙げていた
